# Data model

Status: logical schema for initial migrations
Last reviewed: 2026-11-11

## Conventions

- Primary keys are UUIDs generated by the application and stored portably by SQLAlchemy.
- All timestamps are timezone-aware UTC. `created_at` values are immutable; `updated_at` changes only on mutable operational rows.
- Dates whose day is not known use separate year/month/day columns or a precision enum; the database never invents the first day of a month.
- Enumerations are lowercase strings with database check constraints.
- Raw provider payloads and flexible provider configuration use JSON. Candidate facts and common job fields use normalized columns/tables.
- Text comparisons use explicit normalized keys; original spelling is retained separately.
- Deletes are not cascaded from candidates in normal application code. Historical profile, source, run, and provenance rows are append-only.

## Profile aggregate

### `candidates`

Stable root, one row per person.

| Column | Notes |
| --- | --- |
| `id` | primary key |
| `display_name` | nullable until known |
| `current_profile_version_id` | nullable FK, set after first successful version |
| `current_preference_version_id` | nullable FK |
| `created_at`, `updated_at` | UTC timestamps |

Contact information is versioned rather than stored on this mutable root.

### `source_documents`

| Column | Notes |
| --- | --- |
| `id`, `candidate_id` | primary/FK |
| `source_type` | `resume_pdf`, `repository`, `candidate_input`, or future type |
| `original_name` | display metadata, never used as a filesystem path |
| `storage_key` | content-addressed relative key |
| `sha256`, `mime_type`, `byte_size`, `page_count` | validated source identity |
| `extractor_name`, `extractor_version` | reproducibility |
| `extraction_status` | `pending`, `succeeded`, `partial`, `needs_ocr`, `failed` |
| `extracted_text` | exact extracted document text; private |
| `ingested_at` | UTC timestamp |

Unique constraint: `(candidate_id, sha256, source_type)`.

### `source_fragments`

Addressable source evidence.

| Column | Notes |
| --- | --- |
| `id`, `source_document_id` | primary/FK |
| `page_number`, `section_name` | nullable location |
| `start_offset`, `end_offset` | nullable offsets in extracted text |
| `source_text` | exact text |
| `extracted_value` | parser value before normalization |
| `source_url` | nullable PDF annotation or external source link |
| `verification_status` | status enum below |
| `extracted_at` | UTC timestamp |

### `ingestion_runs` and `ingestion_issues`

An ingestion run records candidate, document, parser name/version, started/completed times, status, resulting or existing profile version, semantic no-op flag, and error code. Issues have code, severity, message, fragment/entity reference, and structured context. Unique request identity is `(candidate_id, source_document_id, parser_name, parser_version, mode)`.

### `profile_versions`

Immutable snapshot header.

| Column | Notes |
| --- | --- |
| `id`, `candidate_id` | primary/FK |
| `version_number` | monotonically increasing per candidate |
| `previous_version_id` | nullable self-FK |
| `source_document_id` | source that caused this version; nullable for manual edits |
| `semantic_hash` | hash of canonical facts, links, and statuses |
| `change_summary` | machine-generated JSON counts/keys |
| `created_at` | UTC timestamp |

Unique constraints: `(candidate_id, version_number)` and `(candidate_id, semantic_hash)`. The latter makes a semantically identical snapshot a no-op even if reached through another import.

### `candidate_details`

One-to-one with a profile version. Contains professional name, professional summary, email, phone, LinkedIn URL, GitHub URL, current location, and a source fragment per populated value. Unknown fields remain NULL. Contact values are not included in logs or example assertions.

### `profile_entities`

Supertype for evidence-bearing records.

| Column | Notes |
| --- | --- |
| `id`, `profile_version_id` | primary/FK |
| `entity_type` | `experience`, `project`, `education`, `contribution`, `achievement` |
| `identity_key` | deterministic normalized identity within the version |
| `display_order` | stable resume order |
| `verification_status` | status enum |
| `source_fragment_id` | nullable primary supporting fragment |

Unique constraint: `(profile_version_id, entity_type, identity_key)`.

Subtype tables have `entity_id` as both primary key and FK:

- `experiences`: organization, role, location, work arrangement, start/end date components and precision, employment type.
- `projects`: name, short description, problem addressed, repository URL, documentation URL.
- `education`: institution, degree, discipline, location, start/end date components and precision, expected graduation flag, academic details.
- `contributions`: repository, pull-request/issue reference, contribution type, status, evidence URL.
- `achievements`: name, issuer/organization, date components and precision, description.

Employment/internship and project rows cannot share subtype tables, even when a project was performed during an internship. They are connected through evidence edges and optional `entity_relationships`.

### `entity_statements`

Long-form facts remain separate and source-addressable.

| Column | Notes |
| --- | --- |
| `id`, `entity_id` | primary/FK |
| `statement_type` | `responsibility`, `achievement`, `architecture`, `contribution`, `outcome`, `technical_change`, `description`, or `other` |
| `text` | source-faithful statement |
| `ordinal` | display order |
| `source_fragment_id` | required FK when extracted |
| `verification_status` | status enum |

### Skill catalog and profile skills

`skill_catalog` stores canonical name and category. `skill_aliases` maps a normalized alias uniquely to a catalog skill. `skill_relationships` stores directional `related_technology` links between catalog records and must not be interpreted as candidate proficiency.

`profile_skills` stores:

| Column | Notes |
| --- | --- |
| `id`, `profile_version_id`, `skill_id` | primary/FKs |
| `candidate_proficiency` | nullable exact candidate-provided label |
| `proficiency_source_fragment_id` | required if proficiency is populated |
| `verification_status` | trust of the claim, not proficiency |
| `last_verified_at` | nullable |

Unique constraint: `(profile_version_id, skill_id)`.

`entity_skills` relates a profile skill to a profile entity and records whether the relation was explicit or parser-associated. It has a unique `(profile_skill_id, entity_id)` constraint.

### `evidence_edges`

| Column | Notes |
| --- | --- |
| `id`, `profile_skill_id`, `entity_id` | primary/FKs |
| `statement_id` | nullable FK to the exact work statement |
| `source_fragment_id` | required FK |
| `classification` | evidence classification enum |
| `explanation` | concise statement of what the candidate did |
| `verification_status` | trust status enum |
| `created_at` | UTC timestamp |

Every `profile_skill` must have at least one evidence edge or produce validation code `skill_without_evidence`. The database cannot express that cross-row rule, so the service and tests enforce it.

### Verification and evidence enums

Verification status:

- `resume_extracted`: asserted by resume text.
- `candidate_confirmed`: explicitly confirmed by the candidate.
- `source_verified`: deliberately checked against an external primary source.
- `unverified`: mentioned but not substantiated.
- `disputed`: conflicting values require review.
- `unknown`: insufficient information.

Evidence classification:

- `direct`
- `partial`
- `transferable`
- `candidate_confirmed`
- `unverified`
- `unknown`

These enums intentionally answer different questions. An edge can be `direct` evidence with `resume_extracted` verification; that does not mean it was externally verified or that the candidate is expert-level.

## Preference aggregate

Preferences are versioned independently so an edit does not rewrite career-history snapshots.

### `preference_versions`

Contains candidate ID, version number, previous version ID, semantic hash, source (`candidate`, `implementation_brief`, or future source), and created timestamp. Candidate and version/hash pairs are unique.

### `preference_items`

| Column | Notes |
| --- | --- |
| `id`, `preference_version_id` | primary/FK |
| `preference_type` | role family, interest, excluded category, opportunity type, arrangement, location, compensation, graduation eligibility, experience, deadline, authorization, DSA focus, or other |
| `value` | nullable normalized text; NULL when explicitly unknown |
| `state` | `target`, `prefer`, `allow`, `avoid`, `exclude`, `unknown` |
| `priority` | nullable integer; no ranking invented when absent |
| `is_hard_constraint` | nullable when not confirmed |
| `operator`, `unit`, `currency` | nullable structured constraint details |
| `source_fragment_id` | nullable; brief/candidate inputs may use a synthetic confirmation fragment |

The service ensures one stable identity per `(preference_version_id, preference_type, normalized value)`. Required-but-unconfirmed categories receive explicit `unknown` items.

## Validation reports

`validation_reports` identifies candidate, profile version, preference version, validator version, timestamp, and completeness summary. `validation_items` stores severity (`info`, `warning`, `error`), stable code, entity/field reference, message, and structured suggested action. Reports are immutable and can be regenerated with a new validator version.

## Discovery aggregate

### `discovery_sources`

Configured connector instance, not a provider class.

| Column | Notes |
| --- | --- |
| `id`, `name` | primary and unique human name |
| `connector_type` | `greenhouse`, `lever`, or `ashby` initially |
| `board_identifier`, `base_url_region` | non-secret provider address data |
| `enabled` | boolean |
| `config` | filters, rate, and pagination JSON validated by connector schema |
| `last_attempted_at`, `last_successful_at`, `next_due_at` | scheduling state |
| `created_at`, `updated_at` | timestamps |

### `source_checkpoints`

One row per source containing cursor/skip, sync token, watermark, ETag, Last-Modified, response hash, connector schema version, and update timestamp. Connector-specific opaque values stay in JSON. A checkpoint changes only in the same transaction as its persisted page.

### `discovery_runs` and `source_runs`

The parent run stores trigger (`manual`, `scheduled`, `retry`), configuration snapshot, and aggregate status. Each source run stores attempts, fetched/created/updated/unchanged counts, status, error code, timestamps, and checkpoint before/after. Source-run failures do not change successful sibling runs.

### `source_leases`

One row per source with owner token and expiry. Acquisition is an atomic conditional update/insert. A source cannot have overlapping active runs; an expired lease can be reclaimed.

### `retry_items`

Contains source ID, optional source run ID, failure category, attempt count, next attempt, last error code, status (`pending`, `running`, `succeeded`, `abandoned`), and timestamps. Payloads contain checkpoint references, never credentials or full HTTP bodies.

### `jobs`

Canonical vacancy.

| Column | Notes |
| --- | --- |
| `id` | internal job ID |
| `title`, `normalized_title` | source display and dedup key |
| `company_name`, `normalized_company` | source display and dedup key |
| `company_website` | nullable |
| `description_text`, `description_html` | preserved normalized canonical description |
| `application_url`, `canonical_application_url` | nullable/original and dedup key |
| `work_arrangement` | `remote`, `hybrid`, `onsite`, `unknown` |
| `employment_type` | normalized enum or `unknown` |
| `opportunity_type` | `internship`, `full_time`, `research`, `other`, `unknown` |
| `experience_requirements`, `education_requirements`, `graduation_year_restrictions` | nullable text, parser origin recorded separately |
| `compensation_text`, numeric/currency/period columns | nullable; never guessed |
| `posting_date`, `application_deadline` | nullable date/time with precision |
| `status` | listing lifecycle enum |
| `first_seen_at`, `last_seen_at`, `last_verified_at` | UTC timestamps |
| `created_at`, `updated_at` | timestamps |

`job_locations` stores multiple original and normalized location strings, country/region/locality when explicitly provided, and remote scope. `job_skill_requirements` stores canonical/raw skill name, requirement level (`required`, `preferred`, `unknown`), and observation origin.

### `job_source_appearances`

Source provenance for a canonical job.

| Column | Notes |
| --- | --- |
| `id`, `job_id`, `source_id` | primary/FKs |
| `source_job_id` | provider identity |
| `listing_url`, `application_url` | original URLs |
| `source_status` | provider status if stated |
| `raw_payload` | complete JSON snapshot or lossless mapped representation |
| `payload_sha256` | unchanged-item detection |
| `first_seen_at`, `last_seen_at`, `last_verified_at` | timestamps |
| `missing_successful_checks` | lifecycle evidence, reset when seen |

Unique constraint: `(source_id, source_job_id)`. One canonical job may have many appearances.

### `job_field_observations`

Provides field-level traceability and prevents parser output from looking source-stated.

| Column | Notes |
| --- | --- |
| `id`, `appearance_id` | primary/FK |
| `field_name`, `value_json` | observed value |
| `origin` | `source_stated`, `parser_extracted`, `model_inferred` |
| `extractor_name`, `extractor_version` | nullable for direct fields |
| `source_path` | JSON path or textual location |
| `observed_at` | timestamp |

This phase does not produce `model_inferred`, but the value is reserved so later systems cannot blur provenance.

### `deduplication_decisions`

Stores candidate job pair, engine version, signal JSON, numeric confidence, outcome (`merge`, `potential_duplicate`, `separate`, `manual_merge`, `manual_separate`), surviving job ID when merged, and timestamp. Pair ordering is canonical and unique for an engine version.

### `job_lifecycle_events`

Append-only job ID, old/new status, reason code, source appearance/run reference, details JSON, and timestamp. Job status and event are written in one transaction.

## Important invariants

1. Current candidate pointers reference versions belonging to that candidate.
2. A profile version and its entities are immutable after commit.
3. Candidate-confirmed data is never replaced by resume extraction.
4. Every extracted fact can reach one source document through a fragment.
5. Skill proficiency is nullable and never computed from mention counts or evidence confidence.
6. Preferences have their own version chain.
7. Every source appearance belongs to exactly one canonical job at a time and is never destroyed by deduplication.
8. An uncertain duplicate remains two jobs plus a decision record.
9. Checkpoints never advance beyond committed observations.
10. Listing status never represents application status.

SQLite triggers are not used for domain behavior. Services enforce cross-table invariants inside transactions, and integration tests exercise them on the migrated schema.
